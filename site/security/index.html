Security

The whole picture,
including the bad parts.

This is our complete security posture and threat model. Not a summary. It's the same document our own reviewers read.

A device that types into other people's computers should not ask you to take its security on faith. Everything below is published because you cannot stay inside a boundary nobody described to you.

01

Read this first

GhostHID is a keyboard. Anyone who can drive it can type into a logged-in session, and typing into a logged-in session is the same thing as running commands there.

The sentence everything follows from

This is not a device where a security failure means someone wiggles your mouse. An authentication failure here is full compromise of the target machine. No driver, no agent, no EDR hook, no audit trail, behind a USB identity chosen to look like the keyboard already on the desk.

We design from that sentence, not from a softer one. If a control would not hold against “the attacker gets a shell”, we do not call it a boundary.

Plug this into machines you administer. That is not a legal disclaimer. It is the boundary the design actually assumes, and the rest of this page explains exactly where it sits.

02

What guards what

BoundaryGuarded by
Radio range → the device's own APWPA2 with a per-device random passphrase, set on first boot
The AP or your LAN → the WebSocketPairing token on every command; browser-origin and Host checks; auth attempts throttled
A screen server → HID inputMutual TLS with the server's certificate pinned, when kvm_tls is on
The target machine → the deviceNothing while unsealed (deliberate, see non-goal 1). Sealed: no serial interface exists on the bus at all.

Three details there are the ones reviewers ask about.

The token gates commands, not the connection. A peer that reaches the socket still cannot type, read config, push firmware or export settings. Refusing at the command layer rather than the door is what makes “reached the socket” a non-event.

WebSockets ignore the browser's same-origin policy, so a page you never opened could otherwise reach the device from your own browser. The handshake's Origin is checked against the device's real address, and the Host header is cross-checked to blunt DNS rebinding.

Secrets are write-only across the network. The Wi-Fi passphrase, AP passphrase and pairing token can be set but never read back. The API reports only whether each is set, and the serial console masks them. This holds against the network. It does not hold against someone holding the board.

03

What it defends against

  • Someone in range who wasn't given the passphrase. The access point is WPA2, never open. Each device generates its own random passphrase and token on first boot, so no two boards share credentials and there is no published default to guess. A stored passphrase that fails validation is re-randomised rather than silently bringing the AP up open.
  • A drive-by from another web page. Origin and Host are checked explicitly, because WebSockets are not covered by the same-origin policy. A page you did not open cannot reach the socket.
  • Token guessing. Repeated auth failures trip an escalating cooldown and drop the connection; an unauthenticated connection that squats the client slot is timed out. Guesses cannot be sprayed at line rate, and the slot cannot be held against you.
  • An unauthenticated peer on your network. The token gates every HID command, every config read and write, the firmware-update endpoint and the config export.
  • Recovering the token, or forging input, from the network. The token is never transmitted. A controller proves it with a challenge-response handshake over a fresh random nonce. Once authenticated, every input command carries a MAC and a monotonic counter, so a peer who captures traffic can't replay it, tamper with it, or synthesise input of their own.
  • Reading your secrets back out over the network. Credentials are write-only, as above.
  • A rogue screen server. With kvm_tls on, the connection is mutual TLS against a certificate you pinned. Nothing else can feed input down that path.
  • Keys stuck down on the target. Three independent layers: the disconnect handler releases everything immediately; a watchdog releases everything if a controller holds input then goes silent for 750 ms; and the BOOT button is a physical panic release that needs no network at all.
  • A failed update. Dual-slot OTA: an interrupted upload leaves the running firmware untouched.
  • The target machine taking over the device, once sealed. A sealed device enumerates HID-only: there is no serial interface on the USB bus for a process on the target to talk to. Undoing it takes a five-second physical BOOT hold, a reboot, and an explicit unseal command; the window is one-shot, so a device left alone comes back HID-only on the next boot. This is the answer to non-goal 1, and the reason to seal anything you deploy and walk away from.
04

What it does not defend against

Non-goals, not oversights. Anyone deploying this should be able to recite them.

  1. The machine you plug it into, unless the device is sealed. On an unsealed device the USB serial console has no authentication, so any process on the target can reconfigure it: repoint the Wi-Fi, change or clear the pairing token, factory-reset it. It cannot read your passwords, but it can take the device over across the USB boundary. Sealing closes this by removing the serial interface from the bus entirely. Treat an unsealed device plugged into a machine you do not administer as that machine's device.
  2. Anyone who has the token. It is a bearer credential: no per-user identity, no revocation beyond changing it, and no record of who used it.
  3. Reading what a session sends. The token itself is safe on the wire: since 0.9.0 it's proven by challenge-response and never transmitted, and input travels in a MAC'd, counted envelope that can't be forged or replayed. What isn't encrypted is the content: the transport is still ws:// / http://, so a peer who already holds the AP passphrase and captures the traffic can read what a session does (the keys you send) without being able to recover the token or inject input. A TLS control plane would close this; it's the accepted residual gap.
  4. Local flash extraction. Storage is not encrypted and secure boot is not enabled, deliberately, so the Wi-Fi passphrase, pairing token and TLS private key are readable by anyone who can put the board into download mode. Treat the token as also granting “dump every secret”.
  5. Firmware you choose to flash, by design. This is a bring-your-own-board project: the device runs whatever image you give it. The token is therefore the power to install firmware.
  6. A screen server reached with kvm_tls off. Plain TCP, no authentication of the peer. The setting exists for bench use; leaving it off in the field hands a keyboard to whoever can win a DNS race.
  7. An image that boots but breaks networking. There is no automatic rollback, so recovery is physical.
05

Why it's built this way

Seven principles. Each is listed with what it cost or caused; a principle that never forced a trade-off is decoration.

  1. Start from the worst case, not the demo

    The threat we model is arbitrary command execution, because that is what the device is. That framing is why the token gates every command rather than merely the connection, why token comparison is constant-time, and why the update path is treated as equal in severity to the keystroke path: installing firmware and typing a command are the same privilege here.

  2. No two devices share a secret

    There is no default password. There never was, and there is nothing to look up. On first boot each board generates its own random AP passphrase and pairing token, seeded from bootloader entropy before the radio is up. Two GhostHIDs side by side have nothing in common an attacker can reuse.

  3. Fail closed, and be loud about it

    An invalid stored passphrase is re-randomised, not quietly restored to a default. An over-long response becomes a well-formed error rather than truncated JSON. A squatting peer is timed out. When the device is unsure it refuses and says so, rather than degrading into something that still works but no longer protects you.

  4. The owner owns the board

    This is a bring-your-own-ESP32 project, and the device must never refuse to run an image its owner flashed. That single commitment rules out the two controls a checklist would demand (secure boot and on-device signature enforcement), and we are comfortable with that, for the reasons below.

  5. If it cannot hold, don't call it a boundary

    We have rejected security features on these grounds and written down why, rather than shipping them for the feature list. An arm/disarm model was dropped as incompatible with the unattended use case. A proposed keystroke-filtering mode is documented as friction and a tripwire, not a boundary, including which bypass path stays open, and why closing it would be worse.

  6. A stuck key is a security bug

    The worst thing this device can physically do to a target is hold a modifier down. That gets three independent layers, not one. Any of them can fail without the other two caring.

  7. Publish the gaps

    The list of things this device does not defend against sits in the documentation in the same voice as the features, and on this page above the philosophy rather than below it. A user who does not know the boundary cannot stay inside it.

06

Decisions we made on purpose

Six places we did not do the obvious thing. The reasoning matters more than the conclusion.

No secure boot, no flash encryption

Locking the board to signed images only defends against a physical attacker replacing firmware, a threat this device already concedes, because anyone holding the board can read storage regardless. The cost is burning one-way fuses, bricking on a mistake, and permanently converting a bring-your-own board into an appliance its owner cannot modify. Paying an irreversible price to partially cover a threat we have already accepted is a bad trade.

Signed releases, zero on-device enforcement

Release artifacts will be signed so anyone who wants provenance can verify a download is genuinely ours before flashing it. Verification is operator-side and opt-in. On-device enforcement was considered and rejected twice over: it would defeat the build-your-own premise, and it buys little even on its own terms, since updating already requires the token and the token already grants full keyboard control. Trust for whoever wants it; lock-in for nobody.

Specified, not yet shipped (a gate before first release)

The USB identity is generic, and we say why

The device presents a generic keyboard identity rather than an Espressif one, so the target cannot practically distinguish it from the keyboard already plugged in. That is the product working as intended, and it is also precisely the risk. The two are not separable, so we do not present it as a security feature; it is stated as what makes the deployment boundary matter.

The serial console is open for bootstrap, and removable afterwards

A brand-new board has to be configurable by someone holding it, so the console starts open. The dangerous commands (changing Wi-Fi, changing or clearing the token, factory reset, entering the bootloader) sit behind an unlock gate once a token is set. A full console password was proposed and downgraded on purpose: physical or USB access already implies reading storage, so a password there protects nothing real while making first-run setup worse.

Sealing is the real answer, and it is a stronger one than a password. Rather than protecting the console, it deletes it: the interface is never added to the USB descriptor, so a sealed device offers the target nothing to attack. That constraint is genuinely hardware-shaped (an interface can only join the descriptor before the USB stack starts), which is why sealing takes effect across a reboot rather than at runtime, and why unsealing needs physical hands rather than a network command.

Credentials on the screen need a physical press

The pairing token is shown on the LCD only on a page reached by physically pressing BOOT, and it reverts to the status page after 60 seconds. Hiding it entirely was considered and rejected: it is the only recovery path on a device whose stored config survives a reflash. Requiring physical presence to reveal a credential is the correct shape.

The token stays off the wire; session content is not yet encrypted

As of 0.9.0 the pairing token is never transmitted: a controller proves it knows the token with a challenge-response handshake: the device sends a random nonce, the client returns HMAC-SHA256(token, nonce), and only the proof crosses the wire. Every keystroke and mouse move then rides in a MAC'd envelope with a monotonic counter, so input can't be forged, tampered with, or replayed. The remaining gap, stated as non-goal 3, is confidentiality of the content: the transport is still ws:// / http://, so a peer with the AP passphrase who captures the traffic can read what a session sends, though not recover the token or inject input. Closing it needs a TLS control plane, recorded as an accepted limitation rather than papered over.

07

Deploying it safely

The first-boot credentials get a fresh board talking; they are yours to keep or replace.

  1. Note your per-device credentials. On first boot the AP passphrase and token are randomised and shown on the LCD (press BOOT to cycle to the Wi-Fi page) and on the serial console. Write them down, or set your own.
  2. If you set your own token, make it six or more characters and random. Length only defends the online-guessing path; it does nothing against a network sniffer or against someone holding the board, so six is plenty.
  3. Prefer the device's own access point over joining a shared network. Smaller exposure, and the AP is available regardless.
  4. Unplug it when you're not using it. It is a keyboard; it is only a risk while it is attached to something.
  5. Treat the token like an SSH key. Anyone who has it can type on the target and install firmware.
08

If you defend machines

If you are protecting computers rather than driving them remotely, this device is blocked the way any unexpected HID is blocked: USB device-authorisation policy. USBGuard on Linux, device-installation restrictions by device ID on Windows, an MDM-enforced allowlist on macOS.

The general control is do not accept a newly-enumerated keyboard on a machine that already has one, and it works against GhostHID exactly as well as it works against anything else in this category. The generic USB identity does not evade it, because that control does not depend on recognising the specific device.

We would rather you know that than not.

09

How this gets reviewed

The security review is a living state document, not a log. Every finding is either fixed with the version that fixed it, accepted by design with the reasoning attached, or withdrawn with the argument recorded so it does not get re-raised in six months. Nothing is closed by assertion.

Two habits are worth naming because they are unusual.

Withdrawn findings keep their reasoning. The arm/disarm model, the console password and hiding the on-screen token are all written up as why not, permanently. A reviewer can disagree with the conclusion and argue against the actual argument rather than guessing at it.

Fixes that introduced follow-ups say so. One update-path fix created an ownership-cleanup problem that became its own tracked finding and its own fix, and that lineage is in the document. A review doc that only records wins is not a review doc.

Where things stand today: no open line-level findings. What remains is proposed hardening (a wear-aware audit log, the keystroke tripwire, a test harness for the safety-critical invariants), tracked as design work rather than as defects, because calling design work a defect is how backlogs start lying to you.

The known weak spots, in the order they should worry you: the plaintext control plane, the absence of any audit trail, and the untested safety invariants. All three are on this page, and none of them are secrets.

10

Reporting a problem

Report privately to the maintainer rather than opening a public issue, and expect the finding to be tracked by name: fixed with a version, accepted with reasoning, or withdrawn with the argument. Findings that change the picture above will change this page too.
